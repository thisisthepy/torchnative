# `bfloat16` — the default path, and why it was wrong

`docs/GENERATE.md` §6.2 and §7.2 left two things open. This round closes one of them
completely, moves the other from "unexplained" to "measured and bounded", and implements the
op that was blocking `generate(attn_implementation="eager")`.

측정일 2026-08-28. 호스트 `darwin/arm64`, CPython 3.13.0, 상류 torch 2.13.0 ·
transformers 5.15.1 (`/Volumes/macMini/caches/spike-venv`).
**벤더링 트리는 한 줄도 고치지 않았습니다.**

## 1. §6.2 의 진단이 틀렸다는 것부터

GENERATE.md §6.2 는 원인을 **GEMM 누산 순서**로 특정하고 §7.2 에 "상류 GEMM 의 블로킹을 그대로
재현해야 한다" 로 남겼습니다. 그 진단은 **검증 가능한 형태였고, 검증해 보니 틀렸습니다.**

반증은 상류만으로 됩니다. 상류의 `F.linear` 을 세 가지로 바꿔 같은 모델을 돌렸습니다 —
그대로, k 를 반으로 쪼개 더하기, f64 로 정확히 누산하기. 셋 다 **합법적인 GEMM** 이고 누산
순서만 다릅니다.

```
                      로짓 최대차   토큰
plain                 —            (기준)
split-k               0.508        20/20 일치
exact (f64 누산)       0.281        20/20 일치
```

**누산 순서를 바꿔도 토큰이 안 바뀝니다.** 그리고 로짓은 최대 0.51 움직입니다 —
관측된 11.75 의 **23분의 1** 입니다. 즉 순서로는 11.75 를 설명할 수 없고, §6.2 가 미해결로
남긴 방향("상류 블로킹 재현")을 아무리 파도 그 차이는 사라지지 않았을 것입니다.

같은 방향의 두 번째 확인: bf16 GEMM 을 여러 누산 순서로 재봤더니 상류와의 차이가
**3456개 중 0~1개**였습니다. 순서는 이 폭에서 거의 아무것도 하지 않습니다.

    교훈: §6.2 의 결론은 "다른 후보를 배제했다" 가 아니라 "이것 말고 떠오르는 것이 없다" 였습니다.
    배제를 실제로 해보니 후보가 죽었습니다.

## 2. 진짜 원인 — `aten.add.Tensor` 가 bf16 을 절사한다

### 2.1 어떻게 좁혔나

상류의 **모든 서브모듈 입출력을 캡처해서, 시임에 상류의 입력을 그대로 먹여** 출력을 대조했습니다
(302개). 이러면 "op 자체의 오차" 와 "앞 층에서 흘러온 오차" 가 분리됩니다.

```
kind                       ne/total    worst rel   mods
mlp.up_proj                 47/276480     0.002      30
self_attn.q_proj            15/103680     0.00039    30
input_layernorm              0/103680     0          30      <- 30개 층 전부 비트 일치
```

**어느 op 도 1 ulp 를 넘지 않고, 어긋나는 비율도 1/5000 수준**입니다. 그런데 전체 순전파는
로짓이 11.75 갈립니다. 이 두 사실은 같이 성립할 수 없습니다 — §1 이 증폭으로는 설명이 안 된다고
이미 보였으니까요. **그러므로 위 표에 없는 op 이 범인입니다.**

위 표에 없는 것은 어텐션 코어(rotary + sdpa)뿐이었습니다. 거기만 따로 재니:

```
어텐션 코어 30개, 상류 입력을 그대로 먹였을 때
  L00   1807/3456 원소가 다름 (52%)     rel 0.0075
  ...   평균 60% 가량                    rel 최대 0.016
```

**60%.** Linear 층의 0.01% 와 자릿수가 4개 다릅니다. 다시 rotary 와 sdpa 로 쪼개고,
rotary 를 한 op 씩 밟았습니다:

```
a = q * cos                 0/3456     비트 일치
rotate_half(q)              0/3456     비트 일치
b = rotate_half(q) * sin    0/3456     비트 일치
out = a + b              1233/3456     <- 여기
```

**곱셈 셋은 전부 비트 일치인데, 그 둘을 더한 것만 36% 가 어긋납니다.** 평범한
`aten.add.Tensor` 입니다.

### 2.2 규칙을 이름으로 특정했다

어긋난 원소를 찍어 보면 규칙이 바로 읽힙니다.

```
        a             b        정확한 a+b       시임          상류
-0.69140625  -0.228515625   -0.919921875   -0.91796875   -0.921875
   -1.40625    0.016113281   -1.390136719   -1.3828125    -1.390625
 0.18945312    0.030761719   0.2202148438  0.2197265625  0.220703125
```

첫 줄의 정확한 합은 **두 bf16 값의 정확히 중간**입니다. 상류는 짝수 쪽(`-0.921875`)으로
갑니다 — round-to-nearest-even. 시임은 `-0.91796875`, 즉 **0 쪽으로 버립니다.** 둘째 줄은
중간값도 아닌데 시임이 더 먼 쪽을 냈습니다: f32 가수의 하위 비트를 그냥 **잘라낸** 값입니다.

무작위 20000쌍으로 확정했습니다.

```
bf16 add     RNE 기준과 다름   5248/20000     절사 기준과 다름   0/20000
bf16 sub                        0                              5423
bf16 mul                        0                              9515
bf16 div                        0                              9952
```

**`add` 만, 그리고 절사와 완전히 일치.** `sub`·`mul`·`div` 는 멀쩡합니다.

### 2.3 왜 아무 테스트도 못 잡았나 — 두 가지가 겹쳤다

**(1) 크기.** 같은 네 쌍을 길이만 바꿔 넣어봤습니다.

```
n=1..31    틀린 원소 0
n=32 이상  전부 틀림
```

**31개까지는 맞고 32개부터 틀립니다.** 잘못된 규칙이 벡터화 경로에만 있었습니다. 그런데
`tools/golden/cases.py` 의 `add` 케이스는 **전부 24개 이하**입니다. 골든 하네스는 이 버그가
사는 코드 경로를 **한 번도 실행한 적이 없습니다.**

**(2) 허용오차.** 설령 실행했더라도 `tools/golden/dtypes.py` 의 `TOLERANCES` 는 1 ulp 를
통과시킵니다. 값 비교가 `math.isclose` 이기 때문입니다.

    즉 이 결함은 "테스트가 부족해서" 가 아니라 **"통과할 수밖에 없는 검사"** 때문에 살아남았습니다
    (`CLAUDE.md` §5.5). 그래서 이번에 추가한 케이스는 **허용오차를 쓰지 않습니다** (§4).

### 2.4 왜 1 ulp 가 O(1) 로짓이 되는가 — 편향이기 때문

절사는 **모든 원소를 같은 방향(0 쪽)으로** 민다는 점이 결정적입니다. RNE 의 오차는 평균 0 이라
30개 층을 지나며 상쇄되지만, 절사의 오차는 상쇄되지 않고 **더해집니다.** 잔차 스트림은 층마다
`add` 를 두 번 지나고 rotary 가 한 번 더 지나므로 순전파 한 번에 90번 편향이 쌓입니다.

이것이 §6.2 가 "GEMM 재결합이 30층에서 O(1) 이 된다" 로 설명하려던 현상의 진짜 정체입니다.
재결합은 **상쇄되는** 오차라 §1 에서 본 것처럼 토큰을 안 바꿉니다. 절사는 **누적되는** 오차입니다.

## 3. 고친 것 — `opmath_in`

상류는 reduced float 연산을 `at::opmath_type`(둘 다 `float`)에서 계산하고 **마지막에 한 번**
narrow 합니다. 이 저장소는 그 규칙을 **GEMM 에만** 적용하고 있었습니다 —
`gemm_accumulate_in` 이 정확히 그 함수인데 이름이 GEMM 을 가리키고 있어서, 원소별 연산과
리덕션이 같은 규칙을 필요로 한다는 것이 보이지 않았습니다.

`aten.rs` 에 `opmath_in` 을 두고 `gemm_accumulate_in` 이 그것을 부르게 한 뒤,
**`add.Tensor` · `add_.Tensor` · `add.Scalar` · `sub`/`mul`/`div` 의 공용 경로 · `rsub.Scalar` ·
`sum`/`mean`** 에 적용했습니다. 정수 dtype 은 건드리지 않습니다 (`int64` 를 `float32` 로 넓히는
것은 비트를 잃는 것이지 지키는 것이 아닙니다).

**이것은 "상류보다 정확하게" 가 아니라 "상류와 같게" 입니다.** 상류의 bf16 `add` 도
`float(a) + float(b)` 를 한 번 narrow 한 것이고, 실측으로 그 모델이 20000/20000 일치합니다.

### 3.1 `alpha` 는 그 규칙을 따르지 않는다 — 재서 알았다

`add`/`sub` 의 `alpha` 는 "넓힌 dtype 에서 곱한다" 가 아니었습니다. dtype 마다 다릅니다.

```
bfloat16   alpha 를 bf16 으로 narrow 하고, 곱 결과도 bf16 으로 narrow    0/20000  (alpha 5종 전부)
           넓힌 채로 두면                                            최대 1607/20000 불일치
float16    alpha 만 narrow, 곱은 float 에 둠                          0~1/20000
           곱까지 narrow 하면                                        최대 1246/20000 불일치
```

**두 reduced float 이 서로 반대**입니다. 유도한 것이 아니라 잰 것이고, 상류에서 둘이 다른
커널에 도달한다는 뜻으로 읽습니다. 코드에는 측정값과 함께 그대로 적어 두었습니다.
`float16` 에 남는 1/20000(`alpha=1.7`)은 double-rounding 경계이며, 덮지 않고 측정된 대로
남겼습니다.

`alpha=1` 에서는 세 모델이 전부 같은 답을 냅니다 — 이 저장소의 호출자가 전부 `alpha=1` 이라
**이 규칙은 어느 쪽으로 틀려도 모델에서는 보이지 않았을 것**입니다. 그래서 골든에 넣었습니다.

### 3.2 리덕션도 같은 결함이었다

`sum`/`mean` 은 저장 dtype 에서 누산하고 있었습니다. 상류는 `acc_type<T>`(= `float`)에서
누산합니다 — `cumsum_default` 의 doc comment 가 **이미 그 규칙을 적어 두고 있었는데**
옆의 두 리덕션이 따르지 않았습니다.

```
bf16 sum(dim=1), 64칸 행     고치기 전 168/200 행이 상류와 다름     고친 뒤 0/200
```

SmolLM2 의 RMSNorm 은 f32 로 올려 계산하므로 이 결함은 **이 모델에서는 발현하지 않았습니다.**
다른 모델에서는 발현합니다.

## 4. 실패할 수 있는 검사로 바꿨다

`CLAUDE.md` §5.5. 이번 결함을 살려준 것이 허용오차이므로, 추가한 검사는 **허용오차를 쓰지
않습니다.**

- `tools/golden/cases.py` 에 `_exact_value_check` — dtype·shape·**모든 값을 비트 단위로** 비교.
  `compare.py` 의 기본 파이프라인을 통째로 우회합니다.
- 케이스는 **64 · 128 · 256 원소**입니다. 24개 이하로는 결함이 사는 경로에 닿지 않습니다 (§2.3).
- 값은 LCG 로 뽑습니다. `0.5 + 0.25` 같은 깔끔한 상수는 어떤 반올림 규칙에서도 같은 답이라
  **절사와 RNE 를 구분할 수 없습니다.**
- `test_reduced_float_narrowing_is_round_to_nearest_even_not_truncation` 은 **틀린 답을 명시적으로
  단언에서 배제**합니다 (`assert got != truncated`). 4원소와 64원소 **둘 다** 확인합니다 —
  짧은 쪽만 재면 원래 멀쩡했던 경로를 재는 것입니다.

### 4.1 고장 내서 확인했다

세 가지를 각각 고장 내고 다시 돌렸습니다 (`cp` 백업, `git checkout` 아님).

| 무엇을 깼나 | 무엇이 빨개졌나 |
|---|---|
| `opmath_in` 을 항등으로 (= 이번 결함 재도입) | **골든 80개** · 새 pytest 2개 · 기존 체크포인트 테스트 1개 |
| 인덱싱이 **항상** splice (never front) | 골든 `separated-outer` |
| 인덱싱이 **항상** front (never splice) | 골든 `adjacent-middle`, `adjacent-trailing` |
| `uint8` 을 마스크가 아니라 정수 인덱스로 | 골든 `uint8-is-a-mask-not-an-index` |

인덱싱은 **양방향으로** 확인했습니다. 한 방향만 재면 첫 인덱스 축이 0인 케이스에서 결함이
가려집니다 — 실제로 "항상 splice" 는 골든 1개만 잡았고, 반대 방향이 나머지를 잡았습니다.

## 5. `aten.index.Tensor` — 인덱스 텐서 여럿

`GENERATE.md` §7.1 의 벽입니다. 규칙을 상류에서 직접 재고 구현했습니다.

**그럴듯하게 틀리기 쉬운 세 가지**(전부 실측):

- **결과 축의 위치.** 인덱스가 붙은 축들이 **인접**하면 브로드캐스트 결과를 그 자리에 끼워
  넣고, 하나라도 **떨어져 있으면 맨 앞으로** 옮깁니다. `(2,3,4,5)` 에서 `[i,None,j]` 는
  `(2,3,3,5)`(앞), `[None,i,j]` 는 `(2,2,3,5)`(제자리). **둘 다 rank 4 라서 모양만 보는
  검사는 통과시킵니다** — 값을 봐야 잡힙니다.
- **`None` 은 구분자다.** 이 층에서 `None` 은 "새 축" 이 아닙니다. 상류가 이미 `self` 를
  unsqueeze 한 뒤이고, 남은 `None` 은 `:` 와 똑같이 인접성을 끊는 평범한 미인덱스 축입니다.
  실측: `x[i,None,j]` 와 `x[i,:,j]` 의 `indices` 리스트가 동일합니다.
- **`uint8` 은 마스크지 인덱스가 아니다.** 상류는 `long`/`int`/`byte`/`bool` 을 받는데
  `byte` 를 `bool` 의 폐기된 철자로 취급합니다. 값이 가리키는 위치가 아니라 **참인 위치**를
  모읍니다. 정수로 읽으면 그럴듯한 모양의 틀린 답이 나옵니다.

마스크는 상류처럼(`at::native::expandTensors`) **rank k 마스크를 k 개의 정수 인덱스 텐서로
펼쳐서** 정수 경로에 합류시킵니다. 두 번째 코드 경로가 생기지 않고, 펼친 k 개는 인접·동일
길이라 위 배치 규칙이 그대로 맞습니다.

**28개 케이스를 상류와 대조해 shape · 값 · 에러 문구까지 전부 일치**합니다. 0-d 인덱스, 빈
인덱스, 음수 인덱스, int32, 마스크+정수 혼합, 네 가지 거절 문구를 포함합니다.

`x[0-d bool mask]` 는 **이름을 대고 거절**합니다. 상류가 여기서 답을 주지 않고
`ntensor >= 3 INTERNAL ASSERT FAILED` 로 죽기 때문입니다 — 규칙이 아니라 버그이므로,
재현하지도 않고 있지도 않은 의미를 지어내지도 않습니다.

### 5.1 그래서 eager `generate()` 가 열렸다

```
                 로짓 최대차   argmax   토큰
eager  float32   5.44e-05     일치     20/20 일치
eager  bfloat16  0.469        일치     20/20 일치 (프롬프트 0)
```

`_GENERATE_PATHS` 에 `eager` 를 넣었고,
`test_eager_generate_stops_at_index_tensor_and_says_so` 는 **완화하지 않고 삭제**했습니다.
그 테스트가 서술하던 일이 더는 일어나지 않으므로, 단언을 약화시켜 살려두면 아무것도 증명하지
않는 테스트가 됩니다. 대신 새 테스트가 **eager 가 끝까지 가는 것**과 **그 이유(마스크 빌더가
부르는 바로 그 모양의 다중 인덱싱 호출)** 를 함께 고정합니다.

## 6. 남은 것 — 토큰 완전 일치는 못 했고, 못 한다

프롬프트를 5개로 늘리면 이렇습니다 (dtype 미지정 = bf16 기본 경로).

```
             토큰 일치      로짓 최대차
sdpa         3/5           0.50 ~ 1.69
eager        4/5           0.47 ~ 0.63
```

**완전하지 않습니다.** GENERATE.md 가 쓰던 프롬프트 하나만 보면 둘 다 일치하지만, 그것은
표본이 하나였기 때문입니다.

### 6.1 상류도 자기 자신과 갈린다 — 이것이 판정의 기준선이다

이 숫자가 "시임이 아직 틀렸다" 는 뜻인지 판정하려면 **기준선**이 필요합니다. 그래서 §1 의
split-k GEMM 을 그대로 써서 **상류 대 상류**를 같은 5개 프롬프트로 돌렸습니다. 양쪽 다 진짜
torch 이고, 한쪽만 GEMM 을 합법적으로 재결합합니다.

```
상류 vs 상류 (split-k)      토큰 일치      로짓 최대차
sdpa                        5/5           0.50 ~ 0.75
eager                       4/5           0.50 ~ 0.97
```

**eager 에서 상류가 자기 자신과 1/5 갈립니다.** 로짓 규모도 시임과 같은 자릿수입니다.

이것이 결론을 정합니다:

> **30층 bf16 그리디 디코딩은 마지막 비트 수준에서 카오스입니다.** GEMM 을 어떻게 결합하느냐
> 같은, 어느 구현이든 자유롭게 고를 수 있는 선택이 토큰을 바꿉니다. 따라서 **독립 구현이
> 이 경로에서 토큰 비트 일치를 보장하는 것은 불가능**하고, 그것을 목표로 삼는 것은 상류가
> 스스로 만족시키지 못하는 기준을 세우는 것입니다.

### 6.2 그래도 sdpa 에는 시임 고유의 차이가 남아 있다

위 표를 나란히 놓으면 한 칸이 어긋납니다.

```
                시임 vs 상류    상류 vs 상류
sdpa            3/5             5/5      <- 여기
eager           4/5             4/5
```

sdpa 에서 상류는 자기와 5/5 일치하는데 시임은 3/5 입니다. **그러므로 sdpa 경로에는 GEMM
재결합만으로 설명되지 않는 차이가 남아 있습니다.** 숨기지 않고 미해결로 둡니다.

무엇인지까지는 좁혔습니다. 어텐션 코어를 상류 입력으로 대조하면 고치기 전 60% → 고친 뒤
**32%** 로 줄었지만 0 이 아닙니다. 그리고 이것은 **반올림 규칙 문제가 아닙니다** —
상류의 `_scaled_dot_product_flash_attention_for_cpu` 를 소박한 정식화(f32 로 전부 계산)와
비교하면 **float32 에서도** 4096개 중 3562개가 4.17e-07 만큼 다릅니다. 확률을 입력 dtype 으로
narrow 하는 변형도 재봤지만 더 나빠집니다(2044/4096). 즉 상류의 블록 단위 커널이 하는 재결합을
어느 소박한 정식화도 재현하지 못하며, bf16 에서는 그 f32 수준 차이가 narrow 를 통과하며
1 ulp 로 드러납니다.

**이것이 §1 에서 죽은 "누산 순서" 가설이 실제로 살아 있는 유일한 자리**입니다. 다만 대상이
GEMM 이 아니라 sdpa 이고, 영향은 O(1) 로짓이 아니라 프롬프트에 따라 토큰이 갈릴 수 있는
경계 수준입니다.

### 6.3 이번 회차가 넣지 않은 것

| 항목 | 상태 |
|---|---|
| sdpa 의 블록 단위 재결합 재현 | **미해결.** §6.2. 좁혔고, 고치지 못했습니다 |
| `float16` 의 `alpha`, 표현 불가능한 값 | **1/20000 불일치 잔존** (§3.1). 측정된 대로 남김 |
| `bitwise_or.Tensor` 등 dtype 승격 | **거절 유지** — GENERATE.md §5.2 그대로, 호출자 없음 |
| `use_cache=True` 로 하는 생성 | **미측정.** 이 회차의 판정도 전부 `use_cache=False` |
| 안드로이드 · iOS | **미측정.** 호스트(darwin/arm64)에서만 |
