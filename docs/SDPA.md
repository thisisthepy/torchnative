# `sdpa` — 상류의 블록형 커널을 그대로 재현했다 (기본값은 아니다)

`docs/BF16.md` §6.2 가 **미해결**로 남긴 하나를 닫습니다. 그 절의 문장은
"sdpa 경로에는 GEMM 재결합만으로 설명되지 않는 차이가 남아 있다" 였고, 원인을
`aten::_scaled_dot_product_flash_attention_for_cpu` 의 블록 단위 재결합으로 좁혀 두었습니다.

> **먼저 읽어야 할 것 — 이 커널은 켜져 있지 않습니다.**
> 재현한 커널(`rust/torch_c/src/flash.rs`)은 **T=512 에서 20배 느립니다.** 그래서 기본
> 경로는 candle 이 그대로 유지하고, 이 커널은 **명시적으로 요청할 때만** 닿습니다.
> 측정과 그 판단은 **§12** 에 있습니다. §3 · §5 · §6 의 "비트 일치" 는 전부 **스위치를 켠
> 상태의 주장**이고, 스위치를 끈 기본 경로에 대한 주장이 아닙니다.

측정일 2026-08-28. 호스트 `darwin/arm64`, CPython 3.13.0, 상류 torch 2.13.0 ·
transformers 5.15.1 (`/Volumes/macMini/caches/spike-venv`).
**벤더링 트리는 한 줄도 고치지 않았습니다.**

## 1. 반드시 구분해야 하는 것 — 커널의 일치와 모델의 재현성

`bfloat16` 30층 그리디 디코딩은 **마지막 비트 수준에서 카오스**입니다. 이것은 이 저장소의
추측이 아니라 **상류만으로 재현되는 사실**입니다. `docs/BF16.md` §1 과 §6.1 이 상류의
`F.linear` 을 합법적인 다른 누산 순서(split-k)로 바꿔 상류 자신과 대조했고, 조율 세션이
착지 검증에서 같은 실험을 다시 돌렸습니다.

> **누산 순서만 바꾸면, 상류를 상류와 비교해도 프롬프트 3개 중 1개에서 토큰이 갈립니다.**

즉 **어떤 독립 구현도 이 경로에서 토큰 비트 일치를 보장할 수 없습니다.** 보장하겠다고 쓰는
것은 상류가 스스로 만족시키지 못하는 기준을 세우는 것입니다.

이 회차가 연 것은 그것이 아니라 훨씬 좁은 것입니다:

    이 커널 하나에 관해서는, 같은 입력에 상류와 **같은 비트**를 답한다.
    (bfloat16 · float16. float32 · float64 는 아니고, 왜인지는 §5.)

그 좁은 것에도 값어치가 있습니다 — 어느 층에서 갈렸는지 물을 때 후보가 하나 줄고,
`sdpa` 는 이제 후보가 아닙니다 (§6). 하지만 **모델의 출력이 같아진다는 뜻은 아닙니다.**

## 2. 상류 커널의 모양

`aten::_scaled_dot_product_flash_attention_for_cpu` 는 교과서 공식이 아닙니다.
`rust/torch_c/src/flash.rs` 가 재현한 것은 다음 다섯 가지입니다.

| | 상류가 하는 것 |
|---|---|
| **블로킹** | 질의는 32행(길면 64/256), 키는 512열 단위로 잘라 돕니다. 블록마다 온라인 소프트맥스가 돌고, 새 블록의 최댓값이 이전보다 크면 **누적기 전체에 `exp(이전최대 - 이번최대)` 를 곱합니다** |
| **행렬곱** | 축소 정밀도에서는 BLAS 가 아니라 **자기 자신의 이식 가능한 커널**입니다. 그 커널의 `sum()` 은 **독립적인 부분합 4개를 끝에서 접습니다** — 누적합 하나가 아닙니다 |
| **지수함수** | 확률이 축소 정밀도 버퍼로 갈 때는 `fexp_u20()`, 아니면 `exp_u20()` 입니다. **둘 다 다항식이고 `exp` 와 1 ulp 안에 있지 않습니다** |
| **리덕션 레인** | 행 합은 8개(축소 정밀도) 또는 4개 레인에 나눠 쌓고 **쌍으로** 접습니다. 남는 원소는 두 다항식이 아니라 플랫폼 `exp` 를 씁니다 |
| **나눗셈** | 마지막은 나누기가 아니라 **역수 한 번과 곱하기**입니다. 둘은 마지막 비트에서 다릅니다 |

전부 "어떤 덧셈이 어떤 순서로 일어나는가" 이므로, `flash.rs` 는 텐서 연산이 아니라
**손으로 편 스칼라 코드**입니다. 텐서 라이브러리의 리덕션은 자기 순서를 자유롭게 고르므로,
텐서 연산으로 쓰면 그 순서를 지정할 방법이 없습니다.

## 3. 왜 허용오차로는 안 보였나

`tools/golden/compare.py` 는 이 op 을 `bfloat16` 에 대해 `TOLERANCES` 의 6e-2 로
비교합니다. **bfloat16 의 1 ulp 는 값의 1/256** 이므로, 허용오차는 그것의 열다섯 배입니다.
즉 **모든 원소가 1 ulp 씩 틀려도 골든은 초록**입니다.

그 상태가 실제로 얼마나 컸는지가 이 파일을 연 측정입니다. 상류의 커널을 **소박한 정식화**
(f32 로 점수 전체를 만들고, 행 최댓값을 빼고, 지수·정규화를 한 번에)와 대조했습니다
(`/Volumes/macMini/caches/bf16-scratch/sdpa.py`, `B,H,T,D = 1,2,64,32`):

```
                             다른 원소      최대차
bfloat16  확률을 f32 로       1505/4096     0.00390625   (= bf16 1 ulp)
bfloat16  확률을 bf16 로      2044/4096     0.00390625
float16   확률을 f32 로       1604/4096     0.000488281
float32                      3562/4096     4.17233e-07
```

**`float32` 에서 이미 4096개 중 3562개가 다릅니다.** 축소 정밀도로 내리기 *전*에
그렇습니다. 그러니 이것은 반올림 규칙 문제가 아니라 **재결합 순서** 문제이고,
소박한 정식화로는 어떻게 고쳐도 없어지지 않습니다.

**그래서 이 회차의 검사는 허용오차가 없습니다.** `rust/torch_c/pytests/test_shim.py` 의
`test_sdpa_*` 셋은 전부 `==` 로 비교합니다. 골든에는 §4 가 발견한 **블록 경계를 넘는 도형**을
넣었지만(16개 케이스), 그쪽의 성질은 여전히 허용오차이고 그 사실을 케이스 주석에 적었습니다.

## 4. 재현하면서 나온 것 — 네 가지, 전부 측정으로 갈렸다

`flash.rs` 는 앞선 회차가 배선 없이 남긴 653줄로 시작했습니다. **주석은 비트 일치를
주장하고 있었고, 그 주장은 검증된 적이 없었습니다.** 검증해 보니 틀려 있었고, 아래 넷이
그것을 참으로 만든 변경입니다.

### 4.1 십진수 리터럴은 상수를 **다시 반올림한다** — 11% 불일치의 원인

다항식 계수가 주석에는 16진 부동소수(`0x1.62e43p-1`)로, 코드에는 여덟 자리 십진수
(`6.9314724e-1`)로 적혀 있었습니다. **둘은 같은 `float` 이 아닙니다.**

```
             주석의 16진값                 코드의 십진값               비트
LN2          0.6931471824645996          0.6931472420692444        3f317218 / 3f317219  (1 ulp)
C3 (fexp)    0.5029083490371704          0.5014316439628601        3f00be9a / 3f005dd3
LOWER        -87.68311309814453          -87.34634399414062        c2af5dc1 / c2aeb154
C1 (exp_u20) 0.04189976677298546         0.042050108313560486      3d2b9f17 / 3d2c3cbc
```

열네 개 중 **열한 개가 달랐습니다.** `float` 이 십진수로 왕복하려면 아홉 자리가 필요한데
여덟 자리가 적혀 있었고, 몇 개는 아홉 자리로도 설명되지 않는 다른 값이었습니다.

결과: **`bfloat16` 원소의 11%(25769/226136)가 상류와 달랐습니다.**

고친 방식은 자릿수를 늘리는 것이 아니라 **비트 패턴으로 적는 것**입니다
(`f32::from_bits(0x3f31_7218)`). Rust 에는 16진 부동소수 리터럴이 없으므로 십진수를
쓸 수밖에 없는데, **"이 리터럴은 아홉 자리인가" 를 검사하는 것은 아무것도 없습니다.**
비트 패턴은 한 자리 모자랄 수가 없습니다.

이것을 고치자 25769 → **1** 이 되었습니다.

### 4.2 남은 1개는 Rust 의 실수가 아니었다 — C 재현본도 같은 자리에서 틀렸다

`ln`/`exp` 를 f64 경유로 바꿔 봐도 그 1개는 그대로였습니다. 그래서 **같은 케이스를 앞선
회차의 C 재현본**(`/Volumes/macMini/caches/sdpa-scratch/flashprobe.c`)**으로 돌렸더니
같은 원소가 같은 값으로 틀렸습니다.**

```
lse[0,0,48]   상류 4.438182353973389   C 재현본 4.438182830810547
```

즉 Rust 이식은 C 재현본과 비트 단위로 같았고, **결함은 재현본 자체에 있었습니다.**
앞선 회차가 못 본 이유는 명확합니다 — 그 회차의 마스크 스윕(`drive2.py`)은
**출력 절반만 비교하고 logsumexp 를 비교하지 않았습니다.**

### 4.3 `qk * scale + mask` 는 본체에서 융합되지 않고 나머지에서 융합된다

상류의 `_scale_attn_mask_fusion_kernel` 은 벡터 본체에서 곱셈과 덧셈을 **따로** 하고,
스칼라 나머지에서는 한 문장(`a[i] * val + b[i]`)이라 **컴파일러가 융합**합니다.
네 조합을 전부 재서 갈랐습니다:

```
          body_fma=0 tail_fma=0   body=1 tail=1   body=0 tail=1   body=1 tail=0
bfloat16       0/65508                0/65508         0/65508         0/65508
float16        0/65508                7/65508         0/65508         7/65508
float32      146/65508             2040/65508        93/65508      2052/65508
```

`body=0, tail=1` 만이 축소 정밀도 둘 다에서 0 이고 `float32` 에서도 가장 작습니다.

### 4.4 마스크 본체의 보폭은 **마스크 dtype** 의 벡터 폭이다 — 1/226136 짜리

§4.2 의 남은 1개가 이것이었습니다. 상류는 그 루프를
`Vectorized<mask_t>::size()` 만큼 전진하는데, `mask_t` 는 **누적기(f32)가 아니라 입력
dtype** 입니다. `bfloat16` 마스크면 **여덟 레인**이므로, 70열짜리 블록은 64에서 본체가
끝나고 **여섯 열**이 융합되는 나머지로 갑니다. 넷으로 읽으면 68에서 끝나고 두 열만 남습니다.

두 열 차이가 어떻게 보였는가가 이 항목의 요점입니다:

- **출력에서는 안 보였습니다.** 행 최댓값이 1 ulp 움직이면 확률과 행 합이 같은 비율로
  움직여 **몫에서 상쇄**되고, 남는 것도 `bfloat16` 로 좁히면 사라집니다.
- **logsumexp 에서만 보였습니다.** `bfloat16` 입력이어도 logsumexp 는 `float32` 로
  나오므로, 상쇄되고 남은 1 ulp 가 **가려지지 않습니다.**

그래서 `test_sdpa_reduced_float_matches_upstream_to_the_last_bit` 은 두 반쪽을 **똑같이**
검사합니다. 출력만 봤다면 이 결함은 지금도 남아 있었을 것입니다 — 실제로 앞선 회차가
그랬습니다(§4.2).

고친 뒤: **0 / 226136.**

## 5. `float32` · `float64` 는 비트 일치가 **아니다**

`flash.rs` 를 열었을 때 붙어 있던 주석은 이 부분을 맞게 적고 있었고, 이번에 숫자가
붙었습니다.

```
                        다른 원소          최대차(출력)   최대차(logsumexp)
bfloat16                0/226136          0             0
float16                 0/226136          0             0
float32            159706/226136          2.384e-07     4.768e-07
float64            160562/226136          3.886e-16     8.882e-16
```

### 5.1 왜 — 상류가 그 dtype 에서만 BLAS 를 부른다

축소 정밀도에서 상류가 도달하는 두 행렬곱은 **자기 자신의 이식 가능한 커널**입니다.
`float32`/`float64` 에서는 플랫폼 BLAS(이 호스트에서는 Accelerate)로 갑니다. **BLAS 의
합산 순서는 이식 가능한 것이 아닙니다.** 앞선 회차의 C 재현본이 이것을 직접 갈랐습니다 —
같은 커널의 GEMM 만 Accelerate 로 바꾸면 `float32` **비인과 케이스가 전부 비트 일치**
(0/25600 등)가 됩니다.

### 5.2 인과 마스크가 있으면 Accelerate 로도 안 맞는다

`float32` 는 `exp_u20()` 을 쓰는데, 그 다항식은 **레인이 결합되어 있습니다** — 네 레인 중
하나라도 범위를 넘으면 벡터 전체가 다항식을 버리고 Sleef 의 `expf` 로 갑니다. 인과 마스크가
칠하는 `-inf` 가 자기 그룹의 바일아웃을 유발하고, 대체되는 것은 **Sleef 의 커널**입니다.
이 저장소에는 Sleef 가 없으므로 플랫폼 `expf` 로 대신합니다. C 재현본에서 Accelerate +
인과 케이스가 0 이 아니었던 것(9/256 ~ 602/14976)이 그 잔차입니다.

### 5.3 그래도 이 커널을 `float32` 에도 쓴다 — 재서 정했다

두 가지를 다 만들어 5개 프롬프트로 재고 골랐습니다.

```
f32 경로                       로짓 최대차 (프롬프트 5개)          토큰
flash.rs (채택)                5.34e-05  7.03e-05  5.72e-05  6.87e-05  7.06e-05      5/5
이전의 소박한 정식화            5.34e-05  1.283e-04 7.82e-05  5.72e-05  5.34e-05      5/5
```

## 7. 그런데 토큰은 나아지지 않았다 — 숨기지 않는다

dtype 을 주지 않은 기본 경로(= `bfloat16`), `attn_implementation="sdpa"`,
`generate(max_new_tokens=20, do_sample=False, use_cache=False)`, 프롬프트 5개
(`docs/BF16.md` §6 과 같은 다섯 개):

```
                로짓 최대차                                  토큰 일치
전 (BF16.md)    0.625  0.844  1.688  0.500  0.688            3/5
후              0.469  0.688  0.500  0.469  0.469            2/5
```

**로짓은 좋아졌고(최악 1.688 → 0.688) 토큰은 하나 줄었습니다.** 좋아진 쪽만 적는 것은
정직하지 않으므로 둘 다 적습니다.

### 7.1 토큰 수는 진척의 척도가 아니다 — 스텝 단위로 다시 쟀다

"프롬프트 3개 일치" 는 **연쇄**입니다. 4번째 스텝에서 토큰 하나가 갈리면 나머지 열여섯 개는
다른 문맥에서 생성된 것이라 비교할 의미가 없습니다. 그래서 **상류 자신의 궤적**을 매 스텝
다시 먹여 5 × 20 = 100 번의 그리디 결정을 **각각** 채점했습니다
(`/Volumes/macMini/caches/sdpa-scratch/stepwise.py`):

```
전    갈린 그리디 스텝 3/100
후    갈린 그리디 스텝 3/100
```

**변하지 않았습니다.** 그리고 갈린 세 스텝의 성질이 판정을 정합니다 — 상위 두 로짓의 간격을
같이 재면:

```
후:  프롬프트 1 스텝  8   간격 0        (상류 토큰도 1위와 동점)
     프롬프트 2 스텝 17   간격 0.125    (상류 토큰이 2위)
     프롬프트 4 스텝 10   간격 0.0625   (상류 토큰이 2위)
```

**세 번 다 동점이거나 그에 준합니다.** 첫 번째는 시임 쪽에서 두 토큰의 로짓이 **정확히
같아서** argmax 가 색인 순으로 고른 것입니다. 이것은 "틀린 답" 이 아니라 **bf16 이 두 후보를
구분하지 못하는 자리**이고, §1 이 말한 카오스가 눈에 보이는 모습입니다.

### 7.2 그러므로 남은 자유도는 GEMM 하나다

§6 이 그것을 이름으로 특정합니다: **`nn.Linear`**. `docs/BF16.md` §1 이 이미 "bf16 GEMM 을
여러 누산 순서로 재보니 상류와의 차이가 3456개 중 0~1개" 라고 쟀고, §6 의 15/103680 은 같은
크기입니다. 상류의 블록형 GEMM 을 `flash.rs` 와 같은 방식으로 재현하는 것이 남은 일이고,
**이 회차는 그것을 하지 않았습니다.**

그것을 하면 5/5 가 되는지는 **모릅니다.** 알 수 있는 것은 §6 의 표에서 0 이 아닌 칸이
전부 GEMM 이라는 것뿐입니다. §1 의 이유로, 그것을 다 닫아도 토큰 일치가 보장되지는 않습니다.

## 12. 20배 — 그래서 이 커널은 옵트인이다

§9.1 이 **미측정**으로 남긴 한 칸이 "속도" 였습니다. 그 칸의 문장은 "`flash.rs` 는 스칼라
커널이고 candle 의 행렬곱을 대체합니다 — 판단 전에 재야 합니다" 였고, 재 보니 우려가
맞았습니다.

### 12.1 측정

측정일 2026-08-28. 같은 호스트. **기계가 조용하지 않았습니다** — 다른 에이전트가 하나
돌고 있어 load average 는 11.4 ~ 13.1 (8코어) 였습니다. 그래서 **절대값은 결론에 쓰지
않고**, 두 경로를 **호출 단위로 번갈아** 재서 인접 표본의 비율만 씁니다. 라운드마다의
최솟값을 취합니다 — 잡음이 한쪽으로만 붙기 때문입니다.

도형은 SmolLM2-135M 의 어텐션(`B=1, H=9, D=64`), `is_causal=False`, 마스크 없음.
스크립트는 `/Volumes/macMini/caches/optin-scratch/bench.py`.

```
                기본(candle)   참조(flash.rs)    비율
bfloat16 T=16      0.0421 ms       0.1706 ms     4.05배
bfloat16 T=128     0.4975 ms       9.0397 ms    18.17배
bfloat16 T=512     7.1051 ms     143.8827 ms    20.25배
float32  T=16      0.0371 ms       0.1812 ms     4.88배
float32  T=128     0.4743 ms       9.7878 ms    20.64배
float32  T=512     6.9630 ms     156.1144 ms    22.42배
```

**T 가 커지면 4배에서 20배로 벌어집니다.** 이것은 스칼라 커널이 BLAS 를 대체할 때의
모양입니다: candle 쪽은 두 행렬곱을 `gemm` 에 넘기고, `flash.rs` 는 같은 곱을 순서를
지키기 위해 손으로 씁니다. 순서를 지키는 것이 목적이므로 이 비용은 **결함이 아니라
설계의 값**입니다.

그리고 **어텐션은 모든 순전파의 핫 패스**이며, 이 프로젝트의 목적은 폰에서 도는 것입니다.
그래서 판단은 다음과 같습니다:

> **기본 경로는 candle 이 유지한다. `flash.rs` 는 명시적으로 요청할 때만 닿는다.**

지우는 선택지도 있었지만 지우지 않았습니다. 남겨서 얻는 것이 구체적이기 때문입니다 —
**§4 의 결함 두 개(다항식 상수 11개, 마스크 보폭)는 이 커널을 상류와 비트 단위로 대조하다
나왔고, 허용오차로는 어느 쪽도 보이지 않습니다.** 앞으로 어떤 최적화를 하든 대조할 정확한
것이 하나 있는 편이 낫습니다.

### 12.2 스위치

두 가지 철자가 있고 **같은 하나의 값**을 가리킵니다.

| 철자 | 무엇 | 언제 |
|---|---|---|
| `BW_SDPA_REFERENCE=1` | 프로세스 시작 시 한 번 읽힘 (`_C` 모듈 초기화) | 스위트·스크립트 전체를 켠 채 돌릴 때 |
| `torch._C._shim_sdpa_reference(True)` | 프로세스 안에서 즉시. **이전 값을 돌려주므로 복원할 수 있음** | 케이스 하나만 켤 때 |

**왜 상류의 이름을 쓰지 않았나.** 규정은 "상류에 이미 있는 이름을 쓰는 것이 최우선" 이고,
그래서 기억이 아니라 **벤더링된 상류 트리를 읽어서** 확인했습니다. 맞는 이름이 없습니다:

| 상류의 후보 | 왜 안 맞나 |
|---|---|
| `torch.backends.cuda.enable_flash_sdp` · `torch.nn.attention.sdpa_kernel(SDPBackend.MATH)` | 이것은 **어떤 aten op 을 부를지**를 고르는 것이지, 한 op 을 **무슨 산술로 계산할지**가 아닙니다. 상류의 `MATH` 는 `mul.Scalar`·`expand`·`bmm`·`_safe_softmax` 라는 **다른 op 열**이고, 이 시임은 그것을 `bootstrap.py` 에서 **이름을 대며 거부**합니다(`_safe_softmax` 에 커널이 없음). 이 이름을 빌리면 `enable_flash_sdp(False)` 가 상류에서는 op 열을 바꾸는 자리에서 우리는 덧셈 순서만 조용히 바꾸게 되고, 게다가 `flash_sdp_enabled()` 가 **어느 쪽도 서술하지 못합니다** — 상류의 기본값은 `True` 인데 우리 기본값은 candle 이어야 하기 때문입니다 |

> **Correction (문서 감사, 2026-09):** 괄호 안의 근거("`_safe_softmax` 에 커널이 없음")는 이
> 문서를 쓴 시점에도 이미 사실이 아니었습니다 — `aten._safe_softmax.default` 는 `9612146`
> (이 문서의 커밋 `4cd3bde` 의 조상 커밋)부터 `IMPLEMENTED` 에 있었고 골든으로 대조돼 왔습니다.
> `bootstrap.py` 자신의 주석이 이미 이것을 발견해 적어 두었습니다(2026-09, 이 감사보다 먼저):
> "**The reason given here used to be `_safe_softmax` has no kernel, and that stopped being
> true.** ... every kernel the math backend needs for the 3-D and non-4-D cases is present, and
> what is missing is the *composite* — nobody has transcribed upstream's math-backend op
> sequence." 지금은 그 composite(`_sdpa_math`)도 **작성되어 있습니다** —
> `dropout_p > 0`(train 모드)과 `is_causal`/bool 마스크 경로를 포함해 `bootstrap.py` 에
> 구현돼 있고, 남은 거부는 4-D 가 아닌 query 에 대해서만입니다(§0 표의 "이름을 대며 거부"는
> 이제 이 더 좁은 경우만 가리킵니다). `torch.ops.aten._safe_softmax.default` 를 직접 호출하면
> 성공합니다(실측). 이 표 전체의 결론("이 저장소 자신의 철자를 쓴다")은 바뀌지 않습니다 —
> `enable_flash_sdp`/`sdpa_kernel(MATH)` 는 여전히 백엔드 **선택** 이름이지 op 산술 선택
> 이름이 아니므로, 지금도 안 맞는 이유가 유효합니다. 낡은 것은 괄호 안의 근거 하나뿐입니다.

> <!-- DOCWATCH: symbol-in-file rust/torch_c/src/bootstrap.py _sdpa_math present -->
| `torch.backends.cpu.get_cpu_capability` / `ATEN_CPU_CAPABILITY` | 읽기 전용이고, 환경변수 쪽은 빌드 전체의 **ISA 등급**을 고르는 것이지 한 op 의 참조 구현을 고르는 것이 아닙니다 |
| `torch.use_deterministic_algorithms` | 한 빌드의 **실행 간 재현성**에 관한 것이고, 여기서는 **두 경로 다 이미 그렇습니다.** 사용자는 이것을 문서에 적힌 목적으로 켜는데, 거기에 20배를 매달아 두면 함정이 됩니다 |

그래서 이름은 이 저장소 자신의 철자를 따릅니다 — 환경변수는 `BW_GEMM_THREADING_THRESHOLD`
· `BRAINWAVE_CHECK_BOOL` 과 같은 `BW_` 계열이고, `_C` 위의 이름은 `_shim_target` 이
세운 **`_shim_` 접두사**(= 상류의 것이 아니라 우리 것)를 씁니다.

### 12.3 기본 경로에 비용이 붙지 않았는지

스위치 검사는 `AtomicBool` 의 relaxed 로드 하나이고, op 호출당 한 번입니다. 그것이 정말
공짜인지는 **develop 을 따로 빌드해서** 확인했습니다 (`755f4c3`, 스위치 자체가 없는 빌드).
두 아티팩트를 **프로세스 단위로 번갈아** 4회씩 돌렸습니다:

```
                develop      이 브랜치(기본)   비율
bfloat16 T=16    0.0425 ms      0.0421 ms     0.991
bfloat16 T=128   0.4965 ms      0.4975 ms     1.002
bfloat16 T=512   7.1803 ms      7.1051 ms     0.990
float32  T=16    0.0380 ms      0.0371 ms     0.976
float32  T=128   0.4667 ms      0.4743 ms     1.016
float32  T=512   6.9705 ms      6.9630 ms     0.999
```

**0.976 ~ 1.016 — develop 자신의 반복 산포와 같은 크기입니다.** 검사 비용이 가장 크게
보였어야 할 `T=16`(op 이 40 마이크로초)에서도 차이가 없습니다.

`BW_SDPA_REFERENCE` 를 **호출마다** 읽는 설계는 피했습니다 — `std::env::var` 는 힙 할당과
프로세스 환경 락을 수반하므로 위 표가 이렇게 나올 이유가 없습니다. 다만 **이 쪽은 재지
않았습니다**: 위 숫자는 relaxed 로드 판본의 것이고, 환경변수 판본이 얼마나 비쌌을지는
측정이 아니라 그것을 만들지 않은 근거입니다.

### 12.4 이 스위치를 켤 만한 때

| 상황 | 왜 |
|---|---|
| **정확성 조사** — "이 층에서 왜 갈렸나" | 켜면 `sdpa` 가 용의자에서 빠집니다 (§6). 끄면 빠지지 않습니다 |
| **참조 대조** — 새 커널·새 최적화를 넣고 무엇이 바뀌었는지 볼 때 | 상류를 못 띄우는 환경(안드로이드·iOS)에서도, 프로세스 안에 상류와 비트 일치하는 답이 하나 있습니다 |
| **회귀 게이트** — `pytests` 의 비트 단위 3개와 골든 16개 | 이미 스스로 켭니다. 아래 §12.5 |
| 추론·벤치마크·배포 | **켜지 마십시오.** 20배입니다 |

### 12.5 게이트가 스위치를 켠 채로 돈다

비트 정확성을 지키는 검사는 켜지 않으면 무의미하므로, **자기가 켜고 되돌립니다.**

| 무엇 | 어디서 켜나 |
|---|---|
| 비트 단위 pytest 3개 | `test_shim.py::_sdpa_call` — 모든 호출이 지나는 한 지점 |
| 블록 경계 골든 16개 | `tools/golden/cases.py::_sdpa_block_cases` 의 `run_c` 래퍼. `finally` 로 복원 |

**켜지 않는 것도 의도입니다**: 골든의 *기존* sdpa 케이스들은 그대로 기본 경로를 지납니다.
그것이 이 하네스에서 **기본 경로의 유일한 커버리지**이고, 같이 옮기면 실제로 매 순전파가
지나는 경로가 여기서 측정되지 않게 됩니다.

### 12.6 이 배선이 정말 실패할 수 있는지 (`CLAUDE.md` §5.5)

새로 만든 것을 무력화해 보고, 무엇이 빨개지는지 확인했습니다.

```
무력화한 것                                   결과
flash.rs 의 기본값을 true 로 (= 켠 채 출고)   pytest 1개 FAIL — 나머지 183개는 전부 초록
골든의 run_c 래퍼를 제거 (스위치 안 켜짐)     골든 2758/2760, 2개 FAIL
```

두 줄 다 읽을 값어치가 있습니다.

- **첫 줄이 이 배선의 이유입니다.** 스위치가 켜진 채 출고되면 라이브러리 전체가 20배를
  무는데, **그것을 알아채는 검사는 새로 넣은 하나뿐입니다.** 나머지 183개는 전부 통과합니다 —
  두 경로가 허용오차 안에서 일치하기 때문이고, 그것이 정확히 §3 이 말한, 이 비용이 오래
  눈에 띄지 않을 수 있는 이유입니다.
- **둘째 줄은 골든 16개 중 2개만 잡는다는 뜻입니다.** 이것은 허용오차 케이스이므로 당연한
  결과이고 (§3), 숨기지 않고 적습니다. 잡은 둘은 `q_len=33, is_causal=True` 의
  `logsumexp` 로, **두 번째 쿼리 블록**이 도는 유일한 케이스입니다 — 블록 간 재결합이
  허용오차를 넘는 유일한 자리라는 뜻이고, 애초에 이 16개를 넣은 이유와 같습니다.
  나머지 14개의 값어치는 회귀 감지가 아니라 **경계를 지나는 입력이 크래시하지 않고
  허용오차 안에 든다**는 것입니다.
