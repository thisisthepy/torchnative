# 그래프 캡처 — 문 하나에서 직선 구간을 기록하고, 재생해서 eager 와 대조했다

## 0. 이 문서가 답하는 것

- **무엇을 캡처할 수 있고, 무엇을 못 하는가.** 못 하는 것은 §4 에 전부 이름이 있습니다.
- **가드가 무엇을 보장하는가.** 그리고 무엇은 보장하지 않는가.
- **지금 만든 자료구조가 ExecuTorch 로 갈 수 있는 모양인가.** §5 가 그 판단이고, 근거는
  `torch.Tag.core` 실측입니다. 여기서 잘못 잡으면 나중에 전부 다시 짜므로, 결론만이 아니라
  **무엇이 부족한지 네 가지를 이름으로** 적었습니다.
- **꺼져 있을 때 얼마인가.** §7. 그리고 그 측정이 오염된 조건에서 났다는 것도 §7 에 있습니다.

구현은 `rust/torch_c/src/capture.rs`, 훅은 `aten.rs` 의 `aten_dispatch` 끝 한 줄,
테스트는 `rust/torch_c/pytests/test_shim.py` 의 capture 절(22 개)과 `capture.rs` 의 단위 테스트 2 개입니다.

## 1. 왜 지금, 왜 여기인가

DESIGN.md §11.1 이 문제를 이렇게 적었습니다 — **NPU 는 즉시 실행 장치가 아닙니다.** ANE · NNAPI ·
QNN 은 op 을 하나씩 받지 않고 그래프를 통째로 받아 미리 컴파일합니다. 커널을 하나씩 포팅하는
경로는 커널을 몇 개 포팅하든 그 장치들에 **도달하지 않습니다.** 도달하는 것은 프로그램의 한
*구간*을 통째로 넘기는 것이고, 그러려면 먼저 그 구간을 기록할 수 있어야 합니다.

같은 문단이 이 셰임이 그 일에 유리한 이유도 적었습니다 — **모든 op 이 `_aten_dispatch` 하나를
지납니다.** 상류는 디스패처의 문이 여럿이라 `__torch_dispatch__` 모드, `torch.export` 의 페이크
텐서, dynamo 프레임 평가기를 전부 동원해야 트레이스가 됩니다. 여기서는 문이 하나라서 기록기가
**한 줄**입니다. 그리고 나중에 쓰이는 커널도 그 줄을 우회할 수 없습니다.

```rust
// aten.rs, aten_dispatch 의 마지막
let out = crate::tensor::promote(py, out)?;
if crate::capture::is_active() {
    crate::capture::record(py, op, args, kwargs, &out);
}
```

`promote` **뒤**인 것이 의도입니다. 기록기가 등록하는 신원은 *파이썬이 실제로 들고 다음 op 에
넘길 객체*여야 하는데, 그것은 커널의 반환값이 아니라 `promote` 의 결과입니다. 그리고 meta 경로도
같은 자리를 지나므로 함께 기록됩니다.

## 2. 표면

```python
_C._capture_begin(inputs)      # inputs: 텐서의 list/tuple. 트레이스는 이것들의 함수다
_C._capture_active()  -> bool
_C._capture_reason()  -> str | None    # 기록 중에도 읽을 수 있다 (§4 의 폴백 경로)
_C._capture_abandon()                  # 기록을 버린다
_C._capture_end(outputs) -> CaptureTrace
```

`CaptureTrace` 는 `.guards` · `.constants` · `.nodes` · `.outputs` · `.graph()` · `.replay(inputs)`
와 `len()` · `repr()` 를 가집니다. 값 참조는 `CaptureValue` 라는 별도 타입이고 FX 처럼 읽힙니다 —
`%in0`(플레이스홀더) · `%c1`(상수) · `%3`(노드) · `%3#1`(노드의 두 번째 결과). 튜플이 아니라
타입인 것이 의도입니다: `("node", 0)` 이 참조인지 진짜 튜플 인자인지 구분되지 않는 그래프는
아무도 낮출 수 없습니다.

### 실제로 나오는 것

`nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Linear(8, 3))` 의 forward 를 벤더 트리 위에서
기록한 결과입니다 (테스트 `test_capture_road_through_the_vendored_tree` 가 도는 것과 같은 것):

```
<CaptureTrace 5 nodes, 1 inputs, 4 constants, 1 outputs>

%0 = aten.t.default(%c0)                    ->  [4, 8]  float32
%1 = aten.addmm.default(%c1, %in0, %0)      ->  [2, 8]  float32
%2 = aten.relu.default() {'self': %1}       ->  [2, 8]  float32
%3 = aten.t.default(%c2)                    ->  [8, 3]  float32
%4 = aten.addmm.default(%c3, %2, %3)        ->  [2, 3]  float32

outputs    [%4]
guards     [{'index': 0, 'shape': [2, 4], 'dtype': 'torch.float32', 'device': 'cpu'}]
constants  [[8, 4], [8], [3, 8], [3]]   ← 두 Linear 의 weight/bias
```

세 가지가 여기서 보입니다.

- **`Linear` 는 `addmm` 입니다.** 기록이 그렇게 말하지, 그럴 것이라고 믿는 것이 아닙니다.
- **가중치는 입력이 아니라 상수입니다.** `_capture_begin` 에 선언되지 않은 텐서는 전부 상수가
  되어 그래프에 소각됩니다. 이것이 `ExportedProgram.graph_signature` 가 사용자 입력과 들어올린
  파라미터를 가르는 것과 같은 분할입니다.
- **`relu` 의 인자가 전부 키워드로 옵니다.** 벤더 트리의 `_torch_level_function` 이 디스패치
  전에 모든 인자를 이름으로 바인딩하기 때문입니다(같은 성질이 `check_devices_agree` 의 구멍을
  만든 적이 있습니다 — docs/META.md §5). 기록기는 위치 인자와 키워드 인자를 **온 모양 그대로**
  보관하고 재생 때도 그 모양으로 되돌립니다.

## 3. 재생이 증명하는 것 — 그리고 증명하지 않는 것

재생은 **같은 문으로 되돌아갑니다.** 같은 op 이름, 같은 비텐서 인자, 같은 `_aten_dispatch`.
그러므로 재생이 eager 와 일치한다는 것은 "구현 두 개가 우연히 맞다" 가 아니라

> **기록이 아무것도 잃지 않았다** — 인자 하나, 순서 하나, dtype 하나, 키워드 하나까지.

는 말입니다. 그리고 그것이 델리게이트가 필요로 하는 정확한 성질입니다: **그래프를 그것을 만든
파이썬에서 떼어내도 같은 함수여야 합니다.** 근사가 아니라 비트 단위 일치를 요구하는 이유가
이것입니다 — 조금이라도 다르면 기록이 무언가를 놓친 것입니다.

실측 (`nn.Sequential` 도로, 입력 세 개는 트레이스가 본 적 없는 것):

| | 값 |
|---|---|
| 기록 중 forward | `[-0.011193826794624329, 0.05188283696770668, 0.13667158782482147, ...]` |
| 기록 전 eager forward | 같음 (기록이 답을 바꾸지 않는다) |
| 같은 입력 재생 | 같음 |
| `x*0.5` · `x*-2.0` · `x*7.25` 재생 vs eager | 세 번 모두 **완전 일치** |

**증명하지 않는 것:** 백엔드가 바뀌었을 때도 맞는가. 그건 백엔드가 생겼을 때 **같은 테스트를 한
층 아래에서** 돌리는 일이고, 그때 이 비교는 "기록 대 eager" 가 아니라 "델리게이트 대 eager" 가
됩니다. 지금 세운 것은 그 비교가 성립할 자리입니다.

## 4. 캡처하지 못하는 것 — 전부 이름을 대고 거절한다

DESIGN.md §6 의 규칙이 여기서 특히 중요합니다. **캡처 층은 조용히 틀린 답을 만들기가 유난히
쉬운 자리입니다** — 잘못 기록된 그래프는 올바른 그래프와 똑같이 그럴듯해 보이고, 재생은 예외
없이 성공하기 때문입니다. 그래서 애매한 것은 근사하지 않고 거절합니다.

| 못 하는 것 | 무엇으로 감지하나 | 거절 문구에 담기는 것 |
|---|---|---|
| **제어 흐름 분기** | `aten._local_scalar_dense.default` | op 이름 + "값이 기록에 없으므로 트레이스는 분기의 한 팔이 된다" |
| **인플레이스 · 별칭** | 이름이 `aten.<name>_.<overload>` 꼴 | op 이름 + "변이를 거절해야 별칭이 관측 불가능해진다" |
| **동적 형태** | 가드가 정확한 형태를 요구 (§ 아래) | 본 형태와 기록된 형태를 둘 다 |
| **난수** | `multinomial` · `randint.default` · `randint.low` | op 이름 + "eager 대조가 실패할 수 없게 된다" |
| **텐서가 아닌 결과** | 메타데이터 전용 허용목록 밖 | op 이름 + "그 값이 데이터에 의존하는지 알 수 없다" |
| **걸어 들어갈 수 없는 컨테이너** | 인자가 `dict`/`set` | 타입 이름 + "안에 든 텐서가 그래프에서 빠진다" |
| 중첩 캡처 / 기록 중 재생 / 구간 밖 출력 | 각각 자리에서 | 무엇이 왜 안 되는지 |

### 왜 `_local_scalar_dense` 하나가 제어 흐름 전부를 잡는가

`bootstrap.py` 가 `item()` · `__bool__` · `__float__` · `__index__` 를 **전부 이 하나의 철자로**
내리기 때문입니다. 텐서 값이 파이썬 값이 되는 길이 그것 하나뿐이므로, 그 op 을 거절하는 것이
"텐서 값에 대한 파이썬 분기" 를 거절하는 것과 같습니다. DESIGN.md §6 의 정적 스캔이 소스에서
찾는 것과 같은 규칙의 런타임 쪽 절반입니다.

### 왜 변이를 거절하는 것이 별칭 문제를 없애는가

인플레이스 별칭은 이번 범위 밖입니다. 그런데 **저장소 공유를 모델링하는 대신 변이를 전부
거절하면, 공유가 관측 가능한 유일한 경로가 사라집니다.** 구간 안에 쓰기가 없으면 두 값이 바이트를
공유하든 말든 어떤 답도 달라지지 않습니다. 그래서 트레이스는 가정이 아니라 **구성상** 단일 할당
(SSA) 입니다. 이 거절이 `add_` · `relu_` · `fill_` · `zero_` · `copy_` · `uniform_` · `normal_` 을
한 번에 덮는 것도 같은 이유입니다 — 판정이 torch 자신의 철자 규약(뒤에 붙는 `_`)이라 새 op 이
들어와도 따로 기억할 것이 없습니다.

### 메타데이터인가 데이터인가 — 텐서가 아닌 결과에 그은 선

`aten.is_floating_point.default` 는 dtype 만 읽습니다. dtype 은 가드가 고정하므로 그 답은 **이
트레이스가 받아들이는 모든 입력에 대해 같습니다** — 그래서 기록하고 값을 소각해도 건전합니다.
`aten._local_scalar_dense.default` 는 **바이트**를 읽고, 바이트는 어떤 가드도 제약하지 않습니다.
허용목록을 코드에 명시적으로 둔 것은 이 선이 실수로 넓어지지 않게 하기 위해서입니다.

### 거절의 방식 — 그 자리에서 raise 하지 않는다

**기록은 관측이고, 관측이 관측 대상을 바꾸면 안 됩니다.** 그래서 캡처 불가능한 op 을 만나면 그
자리에서 예외를 던지지 않고 **기록을 오염(poison)시키고 이유를 적은 뒤** 프로그램은 원래
가던 eager 경로로 끝까지 갑니다. 거절은 `_capture_end` 에서 나옵니다 — 거기가 "캡처했다" 는
*주장*을 하는 자리이기 때문입니다.

이 모양이 델리게이트가 필요로 하는 폴백 경로이기도 합니다: 구간을 캡처해 보고, 캡처가 안 된다고
하면 그냥 eager 로 돌린다. `_capture_reason()` 이 기록 중에도 읽히는 것이 그래서입니다.

### 가드가 보장하는 것, 그리고 보장하지 않는 것

가드는 **입력마다 정확한 형태 · 정확한 dtype · 정확한 장치**입니다. 범위도 심볼도 없습니다.

보장하는 것: 기록 안의 모든 중간 형태는 이 입력들로부터 *계산된* 것이므로, 가드를 통과한
입력에 대해 기록된 출력 형태는 전부 참입니다.

보장하지 않는 것:

- **상수는 가드되지 않습니다.** 참조로 붙잡혀 소각되므로 재생은 같은 객체를 씁니다. 그 객체가
  캡처 이후에 제자리에서 바뀌면 재생도 바뀐 값을 봅니다. 가중치를 갈아끼우려면 다시 캡처해야
  합니다. (`ExportedProgram` 의 들어올린 파라미터와 같은 제약입니다.)
- **배치 차원은 자유롭지 않습니다.** 이 층에 그것을 자유롭게 만드는 것이 아무것도 없고, 그런
  척하는 캡처는 형태 의존 상수를 가진 첫 모델에서 틀립니다. 테스트가 이것을 명시적으로 확인합니다.
- **비텐서 인자는 전부 소각됩니다.** `dim=1` 로 기록된 트레이스는 `dim=0` 을 뜻하던 프로그램의
  근사치가 아니라 **다른 함수**입니다.

동적 형태가 가장 값싸게 드러나는 자리는 `split` 입니다 — 재생이 기록과 다른 개수의 결과를
돌려주면 그것으로 걸립니다. 그 검사가 `replay` 안에 있습니다.

## 5. 이 자료구조가 ExecuTorch 로 갈 수 있는 모양인가

**결론: 모양은 맞다. 바꿔야 하는 것은 자료구조가 아니라 그 위에 얹을 패스다.** 근거와, 그럼에도
부족한 네 가지를 아래에 적습니다.

### 대응은 1:1 이다

| FX / `ExportedProgram` | 여기 |
|---|---|
| `placeholder` | `guards` (형태 · dtype · 장치까지 붙어 있음) |
| `get_attr` / 들어올린 파라미터 | `constants` |
| `call_function`, target 이 `OpOverload` | `nodes`, `op` 이 `aten.<op>.<overload>` |
| args 가 `Node` 또는 리터럴의 pytree | `args`/`kwargs` 가 `CaptureValue` 또는 리터럴, list/tuple 중첩 |
| `output` | `outputs` |
| 튜플 결과의 `getitem` 노드 | `%3#1` (노드, 결과 위치) — 동형 |
| `node.meta["val"]` 의 FakeTensor | 노드마다 결과 shape/dtype/device |

op 이 `aten.<op>.<overload>` 로 이름 붙는 것이 특히 중요합니다. 그것이 `torch.ops.aten.<op>.<overload>`
가 해석하는 바로 그 키라서, Edge 낮추기가 각 노드를 찾아볼 수 있습니다. 테스트가 **기록에 나오는
모든 op 이름이 디스패처가 답하는 이름임**을 확인합니다 — 키가 없어서 못 낮추는 노드는 트레이스에
들어올 수 없습니다.

### 부족한 네 가지

1. **방언이 다릅니다 — 기록되는 것은 ATen 이지 Core ATen/Edge 가 아닙니다.**
   실측 (`torch.Tag.core`, 상류 torch 2.13.0):

   | | 개수 |
   |---|---:|
   | `_aten_all_implemented()` | 108 |
   | └ Core ATen | **70** |
   | └ Core ATen 밖 | **38** |

   그리고 위 §2 의 도로가 기록한 `aten.t.default` 가 **바로 그 밖에 있는 것**입니다
   (`addmm` · `relu` 는 core). 즉 이것은 이론적 우려가 아니라 **가장 작은 예제에서 이미 일어나는
   일**입니다. 필요한 것은 자료구조 변경이 아니라 **분해 패스**이고, 벤더 트리에 이미
   `torch/_decomp/decompositions.py` 가 들어와 있습니다 (DESIGN.md §5 의 3 층 구조 중 2 층).
   분해로도 안 풀리는 잔여가 있다는 것은 docs/CORE_ATEN.md §0 이 이미 재 두었습니다
   (`lift_fresh.default` · `max.default`).

2. **stride / dim order 가 없습니다.** `TensorBase` 에 `.stride()` 자체가 없고(docs/META.md §6),
   dense 쪽도 meta 쪽도 stride 를 들고 있지 않습니다. ExecuTorch 의 Edge dialect 는 dim order 를
   요구합니다. **여기가 유일하게 "이 층 밖에서 고쳐야 하는" 항목**입니다 — 텐서 표현에 stride 가
   생기는 날의 문제이지 기록기의 문제가 아닙니다. 기록기는 그날 `TensorMeta` 에 필드 하나가
   늘어납니다.

3. **`graph_signature` 의 *이름*이 없습니다.** 상수는 인덱스로만 식별됩니다. 파라미터의 FQN
   (`0.weight`) 을 붙이려면 `nn.Module` 계층을 알아야 하는데, 이 층은 디스패처 아래에 있어서
   모듈을 보지 않습니다. 이름은 나중에 **위쪽에서** 붙여야 하고, 그때 붙일 자리(상수 인덱스)는
   이미 있습니다.

4. **변이와 별칭을 모델링하지 않습니다.** `ExportedProgram` 은 버퍼 변이를 표현할 수 있습니다.
   여기서는 §4 대로 거절합니다. KV 캐시가 이 벽에 가장 먼저 부딪힐 것입니다.

**다시 짜야 하는 지점은 없습니다.** 1 · 3 · 4 는 이 구조 *위에* 얹는 것이고, 2 는 이 구조 *아래*
에서 텐서 표현이 바뀌면 따라오는 것입니다.

## 6. 수명과 비용 — 기록 중에 무엇을 붙잡고 있나

식별은 **파이썬 객체 주소**입니다. 주소가 재사용되면 서로 다른 텐서가 같은 값으로 보이므로,
기록기는 **자기가 본 모든 텐서에 강한 참조를 붙잡습니다.** 그래서 주소는 기록이 열려 있는 동안
재사용될 수 없습니다.

대가가 있고, 숨기지 않고 적습니다:

- **긴 모델의 활성화가 `_capture_end` 까지 삽니다.** 중간 결과가 전부 붙잡혀 있습니다. 구간이
  길수록 메모리가 그만큼 오래 유지됩니다. `_capture_abandon()` 이 즉시 전부 놓습니다.
- **상수는 트레이스가 사는 동안 삽니다.** 가중치가 트레이스에 묶입니다.
- **리터럴 인자는 파이썬 객체 그대로 붙잡힙니다.** 다시 인코딩하지 않는 것이 의도입니다 —
  dtype · device · memory_format · `None` 에 대한 변환기를 두 벌 쓰면 그 둘이 어긋날 자리가
  생깁니다. 재생은 커널에 **본 것과 동일한 객체**를 넘깁니다.

## 7. 꺼져 있을 때의 비용 — 재봤다

**단일 관문을 깨지 않는다**는 것이 조건이었으므로 A/B 로 쟀습니다. 방법은 docs/DEVICE_ABS.md §6
과 같습니다 — 훅 한 줄만 다른 두 산출물, 가장 싼 op, 2 원소 텐서, 20 만 회 × 7 회 중 최소,
두 산출물을 번갈아 실행.

| | `add.Tensor` | `cat.default` |
|---|---:|---:|
| 1 회차 훅 없음 → 있음 | 376.6 → 378.0 ns (**+0.4%**) | 516.8 → 496.8 ns (**−3.9%**) |
| 2 회차 훅 없음 → 있음 | 360.5 → 360.7 ns (**+0.1%**) | 474.5 → 496.3 ns (**+4.6%**) |

**이 측정은 오염된 조건에서 났습니다.** load average 8~13 (8 코어) — 다른 세션의 rustc, 에뮬레이터
두 대, 다른 에이전트가 함께 돌고 있었습니다. CLAUDE.md 의 규정대로라면 측정은 단독으로 돌려야
하고, 그러지 못했습니다.

그래서 **이 숫자가 지지하는 결론을 좁혀서 적습니다.** `cat` 이 두 회차에서 −3.9% 와 +4.6% 로
**부호가 뒤집혔습니다** — 훅이 op 을 빠르게 만들 수는 없으므로 이것은 순수한 잡음이고, 잡음
바닥이 대략 **±5%, 약 ±20 ns** 라는 뜻입니다. 따라서:

> 이 측정이 말하는 것은 "훅이 +1 ns 다" 가 아니라 **"훅이 잡음 바닥 아래에 있다 — 상한 약 20 ns"**
> 입니다. 두 회차 모두 `add` 가 +0.1~0.4% 로 안정적이었다는 것이 그 상한을 지지합니다.

구조적으로도 그 이상이 나올 데가 없습니다: 추가된 것은 전역 `AtomicBool` 의 relaxed 로드 하나와
분기 하나이고, 분기는 (캡처를 켜지 않는 한) 항상 같은 쪽으로 갑니다. 이 자리에 무엇을 두면
비싼지는 docs/DEVICE_ABS.md §6 이 이미 재 두었습니다 — 인자마다 `String` 할당이 +79 ns 였습니다.

**기록을 켜면** 같은 `add.Tensor` 가 569~617 ns 입니다 (꺼져 있을 때 360~378 ns). 즉 op 당
대략 **+210~240 ns**. 기록기가 인자마다 파이썬 객체를 복제하고 해시맵을 조회하니 당연한
크기이고, 기록은 명시적으로 켜는 것이므로 그대로 둡니다. 줄일 수 있는 자리(주소 조회, keepalive
푸시)는 알고 있고, 지금 최적화하면 **최적화 대상을 모르는 채로 하는 것**입니다.

측정 한계는 docs/PERF.md §0 과 같습니다 — 절대값은 재현되지 않고, 같은 조건에서 잰 A/B 비율만
유효합니다. 벤치 스크립트는 `/tmp/cap_bench.py` 로 저장소 밖입니다.

### 테스트가 실패할 수 있는지 확인했다

초록을 한 번에 받았으므로 **무력화해 보고 빨개지는지** 두 번 확인했습니다.

- **가드 호출 한 줄을 지웠더니** 형태 · dtype · 장치 세 테스트가 전부 빨개졌습니다. 그중 장치
  테스트는 **커널 안쪽에서** 다른 메시지로 죽었는데, 그것이 가드가 문에 있어야 하는 이유를 그대로
  보여줍니다 — 가드가 없으면 `meta` 텐서가 재생 안까지 들어가 `aten.mul.Scalar` 의 "no meta
  kernel" 로 죽습니다. 이름을 댄 거절 대신 관계없는 커널의 혼란스러운 오류가 나옵니다.
- **키워드 인자 기록을 끊었더니** 리터럴 테스트와 벤더 트리 도로 테스트가 빨개졌습니다. 도로가
  기록한 `aten.relu.default` 는 인자가 **전부 키워드로** 오므로(§2), 이 무력화가 그 노드를
  인자 없는 호출로 만듭니다.

### 그 확인에서 나온 함정 하나 — `run.sh` 만으로는 도로 테스트가 낡은 산출물을 잰다

키워드 무력화를 처음 확인했을 때 **도로 테스트는 통과했습니다.** 원인은 무력화가 안 먹힌 것이
아니라 검증 방식이었습니다:

| | 무엇을 읽나 |
|---|---|
| `pytests/run.sh` | 빌드해서 `$TMPDIR` 에 스테이징한 것 |
| 벤더 트리 도로 테스트 (서브프로세스) | `torchnative/src/main/torch/_C.abi3.so` — **`install_shim.sh` 만 갱신한다** |

즉 `run.sh` 를 단독으로 돌리면 도로 테스트(capture · checkpoint · device · meta 넷 다)는
**직전에 설치된 산출물**을 재고, 방금 빌드한 것을 재지 않습니다. `install_shim.sh` 를 먼저
돌리고 다시 무력화를 확인하니 도로 테스트도 빨개졌습니다. §11 의 재현 절차가 `install_shim.sh`
를 먼저 두는 이유이고, 이 성질은 capture 가 만든 것이 아니라 원래 있던 것입니다.

## 9. 미완으로 남긴 것

전부 지금 상태에서 **하지 않기로 한 것**이고, 각각 왜인지 붙였습니다.

| | 상태 |
|---|---|
| 동적 · 심볼릭 형태 | 없음. 가드가 정확한 형태를 요구한다 (§4) |
| 제어 흐름 (`cond` · `while`) | 없음. 만나면 거절한다 (§4) |
| 변이 · 별칭 | 없음. 거절한다. **KV 캐시가 여기 부딪힌다** |
| 난수 | 없음. 거절한다. 델리게이트에 시드를 넘기는 방법이 정해지지 않았다 |
| **구간 자동 선택** | 없음. `begin`/`end` 를 사람이 부른다. 진짜 델리게이트는 "어디부터 어디까지" 를 스스로 정해야 하고, 그 정책은 아직 없다 |
| **트레이스 직렬화** | 없음. 프로세스 밖으로 못 나간다. `.pte` 로 가려면 필요하다 |
| **가드 캐시** | 없음. 같은 형태가 다시 들어와도 자동으로 재사용되지 않는다. 재사용은 호출자가 `replay` 를 부르는 것뿐 |
| 분해 패스 (→ Core ATen) | 없음 (§5-1) |
| stride / dim order | 없음 (§5-2). 이 층 밖 |
| 파라미터 FQN | 없음 (§5-3) |
| **멀티스레드** | 플래그는 전역, 레코더는 스레드 로컬. 스레드 A 가 기록 중일 때 스레드 B 의 op 은 **오염 없이 그냥 기록되지 않는다.** 단일 스레드에서만 검증했고, 다중 스레드 프로그램에서는 조용히 불완전한 트레이스가 나올 수 있다 |
| 백엔드 · 델리게이트 | 없음. 재생은 같은 문으로 되돌아간다 (§3) |

마지막 두 줄이 이 작업이 **아직 아닌 것**입니다. 이것은 가속기가 아니라 **가속기가 붙을 자리**입니다.

## 10. 다음 걸음

순서에 근거가 있습니다 — 각 단계가 다음 단계에 필요한 것을 만듭니다.

1. **분해 패스.** 기록된 ATen 을 Core ATen 으로 낮춥니다. 벤더 트리에 `torch/_decomp/` 가 이미
   있고, 첫 대상은 §5-1 이 지목한 `aten.t.default` 처럼 가장 작은 예제에서 이미 나오는 것들입니다.
   이 단계가 끝나야 "Edge 로 갈 수 있다" 가 주장이 아니라 사실이 됩니다.
2. **구간 선택과 가드 캐시.** 어디부터 어디까지 캡처할지, 그리고 가드가 맞으면 다시 캡처하지
   않는 것. 디코드 루프가 이것의 첫 수혜자입니다 (DESIGN.md §7 — 디코드는 같은 형태의 반복).
3. **직렬화.** 트레이스를 프로세스 밖으로. `.pte` 로 가는 길이 여기를 지납니다.
4. **첫 델리게이트.** §3 의 대조를 한 층 아래로 내립니다 — "기록 대 eager" 가 "델리게이트 대
   eager" 가 됩니다. 그 시점에 §9 의 "백엔드 없음" 이 닫힙니다.

멀티스레드(§9)와 변이(§4)는 이 순서와 무관하게 언제든 걸릴 수 있는 것이므로, 부딪히는 쪽이
먼저입니다.
