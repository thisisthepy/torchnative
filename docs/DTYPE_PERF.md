# `bfloat16`/`float16` vs `float32` — 상류와 대조해서 다시 잰 것

**한 줄 결론.** README 가 원인으로 지목한 `opmath` 규칙은 **원인이 아니었습니다.** 진짜 원인은
`docs/DTYPE.md` 가 만든 축소 정밀도 빠른 경로가 **연속 텐서에만 걸리는데, 실모델의 가중치는
언제나 비연속**(`linear` 이 넘기는 `t(weight)`)이라 **한 번도 발동하지 않고 있었다**는 것입니다.
전치 레이아웃을 보존하며 넓히도록 고쳤고, **비트는 한 개도 움직이지 않았습니다**:

| SmolLM2-135M, `S=128` prefill | 전 | 후 |
|---|---:|---:|
| `bfloat16` | 469.4 ms | **180.7 ms** (2.60× 빠름) |
| `float32` | 155.2 ms | 155.2 ms (변화 없음) |
| 로짓 sha256 | \[동일\] | \[동일\] |

그 결과 **`bfloat16` 이 상류보다 2.04 배 빨라졌고**(상류 368.7 ms), 우리 자신의 `float32` 대비
벌금은 **3.02× → 1.16×** 로 줄었습니다. 같은 자리에서 상류의 벌금은 **4.84×** 입니다.
즉 *"축소 정밀도를 고르면 느려진다"* 는 상류에서 더 심하게 참이고, 이제 우리 쪽이 덜합니다.

---

> **§2 를 먼저 읽고 §3 에서 뒤집힙니다.** 처음 잰 `mm` 마이크로벤치(§2)는 **모델이 절대
> 만들지 않는 레이아웃**을 쟀습니다. 모델 수준 측정(§3)이 그것과 어긋났고, 원인을 찾아보니
> 레이아웃이었습니다(§4). 실제 결론은 §4 이후입니다. §2 를 지우지 않고 남겨둔 이유는
> 그 함정이 이 저장소에서 세 번째이기 때문입니다.

## 0. 이 문서의 숫자로 하면 안 되는 것

- **기계가 공유 중이었습니다.** 다른 에이전트가 동시에 빌드 중이었고 load 는 2.7 ~ 5.9 를
  오갔습니다. 그래서 **같은 실행 안의, 같은 스크립트로 얻은 상대 비교만** 씁니다.
- **호스트(M1, macOS)만 쟀습니다.** 안드로이드·iOS 측정은 없습니다.
- 상류는 이 venv 에 설치된 **torch 2.13.0 의 macOS arm64 휠**입니다. 소스 빌드가 아니고,
  아래 §1 이 보이듯 그 휠의 빌드 플래그가 결과의 원인입니다. **다르게 빌드한 상류에는 이
  숫자가 적용되지 않습니다.**

## 1. 상류를 먼저 쟀다 — 그리고 거기서 답이 나왔다

지시는 *"상류도 같은 규칙을 내는데 상류는 bf16 이 f32 보다 느리지 않을 것이다 — 그것부터
확인하라"* 였습니다. **확인했고, 전제가 틀렸습니다.**

```
$PY -c "import torch; print(torch.__config__.show())"

  BLAS_INFO=accelerate          <- float32 gemm 은 Accelerate(AMX) 로 간다
  USE_MKLDNN=OFF                <- bf16/f16 gemm 백엔드가 아예 없다
  USE_MKL=OFF
  USE_EIGEN_FOR_BLAS=ON
  CPU capability usage: DEFAULT
```

macOS arm64 휠은 **oneDNN 없이** 빌드됩니다. Accelerate 에는 `sgemm`(f32)·`dgemm`(f64)만 있고
`bf16`/`f16` GEMM 이 없으므로, 상류의 축소 정밀도 `mm` 은 붙을 백엔드가 없어
`at::native::cpublas::gemm` 의 **참조 구현**(스칼라 3중 루프, `opmath_t` 누산)으로 떨어집니다.

그래서 상류에서 축소 정밀도는 **느린 정도가 아니라 절벽입니다.**

## 2. 측정 — SmolLM2-135M 의 실제 모양에서

둥근 수가 아니라 모델이 실제로 도는 모양입니다 (`hidden=576`, `intermediate=1536`,
`vocab=49152`, `kv=192`). 같은 스크립트를 `PYTHONPATH` 만 바꿔 두 번 돌립니다 — 넣으면 우리
시임, 빼면 상류.

### 2.1 prefill (S=128) — `bfloat16`

|---|---:|---:|---:|---:|---:|

| `k/v_proj` `[128,576]@[576,192]` | 0.0253 | **3.2143** | 0.0259 | 0.0440 | **73× 빠름** |
| `gate/up` `[128,576]@[576,1536]` | 0.1637 | **74.0521** | 0.1685 | 0.2806 | **264× 빠름** |
| `down_proj` `[128,1536]@[1536,576]` | 0.1638 | **74.3708** | 0.1654 | 0.2556 | **291× 빠름** |
| `lm_head` `[128,576]@[576,49152]` | 21.7444 | **4398.05** | 20.1003 | 23.8742 | **184× 빠름** |
| `residual add` `[128,576]` | 0.0245 | 0.0313 | 0.0047 | 0.0274 | 1.1× 빠름 |
| `swiglu mul` `[128,1536]` | 0.0306 | 0.0381 | 0.0263 | 0.0705 | 0.5× (느림) |

단위 ms, 5 회차의 최솟값. `float16` 도 같은 모양입니다 (상류 `gate/up` f16 74.07 ms).

즉 *"우리가 상류를 못 따라가는 것"* 이 아닙니다. 우리는 f32 에서 상류를 만나고, bf16 에서는
상류를 두 자릿수 배로 앞섭니다.

### 2.3 교대 측정과 대조군 — 위 숫자가 소음이 아니라는 것

`CLAUDE.md` 의 측정 위생: **upstream → shim → upstream → shim → upstream → shim** 으로
3 회차, 각 셀은 프로세스 3 개의 최솟값. 그리고 **대조군**으로 시임을 자기 자신과 비교했습니다.

```
대조군 (shim vs shim) 최대 편차:  1.00 에서 15.3%   (한 셀만; 대부분 5% 이내)
```

| case | 상류 min | 상류 편차 | 우리 min | 우리 편차 | 우리가 몇 배 빠른가 |
|---|---:|---:|---:|---:|---:|
| `q/o_proj` bf16 | 9.6190 | 0.4% | 0.1064 | 0.3% | **90.4×** |
| `k/v_proj` bf16 | 3.2064 | 0.5% | 0.0441 | 10.4% | **72.7×** |
| `gate/up` bf16 | 74.0380 | 0.1% | 0.2759 | 6.7% | **268×** |
| `down_proj` bf16 | 74.2781 | 0.2% | 0.2561 | 5.0% | **290×** |
| `lm_head` bf16 | 4262.79 | 7.7% | 24.3107 | 0.8% | **175×** |
| `gate/up` **f32** | 0.1643 | 0.3% | 0.1685 | 9.3% | 0.98× (동률) |
| `lm_head` **f32** | 19.8353 | 7.3% | 20.2820 | 1.3% | 0.98× (동률) |

**GEMM 쪽 효과(73 ~ 296 배)는 대조군 편차(15%)보다 세 자릿수 큽니다.** 판정에 문제가 없습니다.

**반대로 판정하면 안 되는 칸이 있습니다.** `S=128` 의 elementwise 와 `S=1` 의 작은 op 들은
절대값이 0.001 ~ 0.03 ms 이고 상류 쪽 회차간 편차가 **48 ~ 98%** 까지 벌어졌습니다
(`residual add f32` 98.1%, `swiglu mul f16` 48.3%). 그 칸들의 상류 대비 비(0.45× ~ 2.7×)는
**소음보다 작으므로 미해결로 둡니다.** 아래 §3 의 elementwise 논의는 상류가 아니라
**우리 f32 대비 우리 bf16** — 같은 빌드, 같은 실행 안 — 만 씁니다.

### 2.4 우리가 상류에 지는 자리 — decode 의 `float16`

> **이 절의 "유일한" 은 §4 에서 틀린 것으로 판명됩니다.** 연속 레이아웃에서는 여기 한 칸만
> 졌지만, 모델이 실제로 쓰는 전치 레이아웃에서는 **`mm` 전부**를 지고 있었습니다.

| S=1 | 상류 f16 | 우리 f16 | |
|---|---:|---:|---|
| `lm_head` `[1,576]@[576,49152]` | **3.4474** | 6.2290 | 상류가 **1.81× 빠름** |
| `gate/up` `[1,576]@[576,1536]` | **0.0781** | 0.0881 | 상류가 1.13× 빠름 |
| `down_proj` `[1,1536]@[1536,576]` | 0.0858 | 0.0839 | 동률 |

상류의 f16 `lm_head` 는 자기 f32(3.2072)에 **0.24 ms 밖에 안 붙습니다** — 가중치를 `float32`
로 **실체화하지 않는** gemv 커널(aarch64 `fp16_gemv_trans` 계열)이 있다는 뜻입니다.
우리는 `[576,49152]` = 2830 만 원소를 매 호출 넓히므로 f32 대비 +3.03 ms 가 그대로 붙습니다.
같은 자리에서 상류 **bf16** 은 33.43 ms 이므로(그 커널이 bf16 에는 없음) 우리가 5.35× 앞섭니다.

즉 이 한 칸은 **`opmath` 규칙의 비용이 아니라 융합 gemv 의 부재**입니다. `docs/DTYPE.md` §4.3
이 프로토타입까지 만들고 "캐시에 들어가는 크기에서는 Accelerate 가 이긴다" 로 남겨둔 항목이고,
`lm_head` 는 그 표의 1024² 와 달리 **56 MB 짜리 DRAM 바운드** 라 부호가 반대일 수 있습니다.
§7 에서 다룹니다.

## 3. 모델 수준 — 마이크로벤치와 어긋났다

SmolLM2-135M, `S=128` prefill, 같은 토큰 128 개. `from_pretrained` 로 실제 체크포인트.

| | 상류 | 우리 | 우리/상류 |
|---|---:|---:|---:|
| `float32` prefill | **76.1 ms** | 155.4 ms | 2.04× 느림 |
| `bfloat16` prefill | **368.7 ms** | 469.6 ms | 1.27× 느림 |
| **bf16/f32 (자기 자신 대비)** | **4.84×** | **3.02×** | |

**§2 가 예측한 것과 전혀 다릅니다.** §2 의 `mm` 표대로면 상류 bf16 prefill 은 30 개 층 ×
층당 247 ms = 7 초여야 하는데 **368.7 ms** 입니다. 20 배 어긋났습니다.

그리고 이 표가 §2 의 결론을 뒤집습니다:

- 상류도 bf16 이 f32 보다 **4.84 배 느립니다.** "상류는 bf16 이 안 느릴 것" 이라는 전제는
  틀렸지만, 이유는 §2 가 말한 절벽이 아닙니다.
- **우리의 bf16 벌금(3.02×)이 상류의 벌금(4.84×)보다 오히려 작습니다.**

## 4. 어긋난 이유 — 레이아웃. 모델은 `mm` 을 그 모양으로 부르지 않는다

`nn.Linear` 는 `x @ W.t()` 를 계산하고, `W` 는 `[out,in]` 연속입니다. 즉 두 번째 피연산자는
**전치된 뷰**(비연속)입니다. §2 는 `[in,out]` **연속** 텐서를 넘겼습니다 — 모델이 만들지 않는
레이아웃입니다. 두 레이아웃을 같이 재면:

### 4.1 상류: 전치 레이아웃에 축소 정밀도 빠른 경로가 있다

| 상류, S=128 | dtype | `mm` B 연속 | `mm` B 전치 | 배수 |
|---|---|---:|---:|---:|
| `gate/up` | bf16 | 74.1531 | **1.9693** | **37.6×** |
| `down_proj` | bf16 | 74.3376 | **1.8899** | **39.3×** |
| `lm_head` | bf16 | 4275.02 | **75.07** | **56.9×** |
| `lm_head` S=1 | bf16 | 33.5026 | **1.0254** | **32.7×** |
| `gate/up` | f32 | 0.1637 | 0.2274 | 0.7× |

**`float32` 는 레이아웃에 거의 무관한데 축소 정밀도만 37 ~ 57 배 차이납니다.** 상류에는
전치된(=`NT`) 축소 정밀도 GEMM/GEMV 커널이 있고, §2 는 그것이 없는 쪽을 골라 재고 있었습니다.

**그리고 `S=1` 에서 상류의 bf16(1.0254)은 자기 f32(3.5578)보다 3.5 배 빠릅니다.**
디코딩은 메모리 바운드이므로 바이트를 절반만 읽는 쪽이 이깁니다. 즉 *"이 하드웨어에서 축소
정밀도는 빨라질 수 없다"* 는 **거짓입니다** — 상류가 그 자리에서 해내고 있습니다.

### 4.2 우리: 전치 레이아웃이 오히려 **최악**이다

| 우리, S=128 | dtype | `mm` B 연속 | `mm` B 전치 | |
|---|---|---:|---:|---|
| `gate/up` | bf16 | 0.3417 | **2.3250** | 6.8× **나빠짐** |
| `down_proj` | bf16 | 0.2742 | **2.1412** | 7.8× 나빠짐 |
| `lm_head` | bf16 | 25.3637 | **89.0161** | 3.5× 나빠짐 |
| `lm_head` S=1 | bf16 | 6.6988 | **69.5999** | **10.4× 나빠짐** |
| `lm_head` S=1 | f32 | 3.8073 | 3.0977 | 좋아짐 |

**모델이 실제로 쓰는 레이아웃에서 우리는 상류에 진다:**

| S=1 `lm_head` (디코딩 1 토큰) | bf16 |
|---|---:|
| 상류 | **1.0254 ms** |
| 우리 | **69.5999 ms** |
| | **68× 느림** |

### 4.3 원인 — `fast_to` 가 비연속에서 candle 로 떨어진다

```rust
// rust/torch_c/src/reduced.rs:324
if src == target || !t.device().is_cpu() || !t.layout().is_contiguous() {
    return t.to_dtype(target);          // <- candle 의 원소 단위 경로
}
```

`docs/DTYPE.md` 가 만든 NEON 변환 경로는 **연속 텐서에만** 겁니다. 그런데 실모델에서 여기
도착하는 가중치는 **항상 비연속**입니다(`linear` 이 넘기는 `t(weight)`). 그래서:

1. NEON 변환이 **한 번도 발동하지 않고**, candle 의 스칼라 경로를 탑니다.
2. 더 나쁜 것: candle 의 `to_dtype` 는 결과를 **연속으로 실체화**합니다. 그래서 전치 뷰가
   사라지고, `gemm_with_layout_fallback` 이 지키려고 만들어진 `CblasTrans` 도 같이 사라집니다
   — `lm_head` 에서 113 MB 를 strided gather 로 다시 씁니다.

`docs/DTYPE.md` 의 최적화는 **연속 레이아웃에서 측정되고 연속 레이아웃에서만 발동하는데,
모델은 그 레이아웃을 만들지 않습니다.** 그것이 §2 와 §3 이 20 배 어긋난 이유 전부입니다.

## 5. 무엇을 고쳤나

`rust/torch_c/src/aten.rs` 에 `widen_gemm_operand` 하나를 추가하고, GEMM 피연산자를 넓히던
5 개 자리가 그것을 부르게 했습니다 (`mm` · `bmm` · `matmul` · `addmm` · `baddbmm`).

```rust
fn widen_gemm_operand(t: &Tensor, acc: DType) -> candle_core::Result<Tensor> {
    if t.dtype() == acc || t.layout().is_contiguous() || t.rank() < 2 {
        return t.fast_to(acc);
    }
    // 알아볼 가치가 있는 레이아웃은 "연속 텐서의 전치" 하나 -- `linear` 이 만드는 바로 그것.
    if let Ok(base) = t.t() {
        if base.layout().is_contiguous() {
            return base.fast_to(acc)?.t();
        }
    }
    t.fast_to(acc)
}
```

**연속인 base 를 NEON 으로 넓히고 전치를 도로 씌웁니다.** 그래서

1. `docs/DTYPE.md` 의 NEON 변환이 실모델에서 **처음으로 실제로 발동하고**,
2. 결과가 **전치 뷰로 남으므로** `CblasTrans` 가 살아 있고 113 MB 재수집이 사라집니다.

`addmm`·`baddbmm` 은 애초에 `fast_to` 가 아니라 `to_dtype` 를 부르고 있었으므로
(빠른 경로가 연결된 적이 없습니다) 같이 옮겼습니다. `mm` 은 이제 다른 넷과 같이
`gemm_with_layout_fallback` 을 지나갑니다 — 전치 피연산자를 candle 이 거절하는 백엔드에서
예전처럼 복사로 떨어지게 하는 안전망입니다.

### 5.1 왜 값이 움직일 수 없는가

변환은 **원소별**이고, 전치는 **어느 원소가 어디에 앉는지를 바꿀 뿐 원소를 바꾸지 않습니다.**
그러므로 두 연산은 교환됩니다:

```
widen(x.t())  ==  widen(x).t()        원소마다, 비트마다
```

허용오차 논증이 아니라 항등식입니다. `docs/GENERATE.md` §6 이 기록한 "상류가 bf16 에서
누산 순서에 따라 자기 자신과 불일치한다" 는 함정에 걸리지 않는 이유가 이것입니다 —
**누산 순서를 건드리지 않았습니다.** GEMM 에 도착하는 값도, 그 값을 더하는 순서도 그대로이고,
바뀐 것은 그 값을 만드는 데 쓰인 명령과 결과 텐서의 stride 뿐입니다.

## 7. 남은 것 — 그리고 이제 상류에 지는 자리는 하나다

고친 뒤, 모델이 쓰는 레이아웃에서:

| S=128 prefill, bf16 | 상류 | 우리 (후) | |
|---|---:|---:|---|
| `q/o_proj` | 0.7601 | **0.1310** | 5.8× 빠름 |
| `gate/up` | 1.9693 | **0.3330** | 5.9× 빠름 |
| `down_proj` | 1.8899 | **0.3326** | 5.7× 빠름 |
| `lm_head` | 75.07 | **13.99** | 5.4× 빠름 |
| **`lm_head` S=1 (디코딩)** | **1.0254** | 6.3569 | **상류가 6.2× 빠름** |

**남은 한 자리는 디코딩의 `lm_head` 이고, 이것은 이 고침으로 닿지 않습니다.**
`S=1` 에서 가중치를 넓히는 것은 O(n²) 작업인데 gemv 도 O(n²) 이라 **상각될 여지가 구조적으로
없습니다.** 넓히기를 아무리 빠르게 해도 `[576,49152]` = 2830 만 원소를 `float32` 로
**실체화**하는 한 f32 gemv 비용이 그대로 더해집니다(6.36 = 3.07 + 3.3).

상류는 그 자리에서 **융합 gemv**(가중치를 축소 정밀도로 읽고 `float32` 로 누산, `float32`
텐서를 만들지 않음)를 써서 자기 f32(3.5578)보다도 **3.5 배 빠릅니다.** 디코딩은 메모리
바운드이므로 바이트를 절반만 읽는 쪽이 이기는 것이 정상입니다.

> 따라서 *"이 하드웨어에서 축소 정밀도는 빨라질 수 없다"* 는 **틀린 결론입니다.**
> 디코딩에서는 빨라질 수 있고, 상류가 그것을 하고 있으며, 우리에게 없는 것은
> **융합 gemv 커널**입니다. `docs/DTYPE.md` §4.3 이 프로토타입까지 만들고
> "캐시에 들어가는 1024² 에서는 Accelerate 가 이긴다" 로 접었는데, `lm_head` 는
> 56 MB 라 그 표의 영역 밖입니다. **부호가 다를 수 있고, 이 회차에서 재지 않았습니다.**

### 7.1 확인하지 않은 것

| 항목 | 상태 |
|---|---|
| 융합 gemv 가 `lm_head` 크기에서 이기는가 | **미측정.** §7 의 근거는 상류가 해낸다는 것뿐 |
| 안드로이드 · iOS | **없음.** 호스트만 |
| `float32` prefill 이 상류의 2.04 배인 이유 | **이 회차 범위 밖.** GEMM 은 동률(§2.3)이므로 원인은 GEMM 이 아닌 곳 |
| elementwise 의 `bfloat16` 벌금 | `docs/DTYPE.md` §4.1 이 이미 설명 (M1 에 `BFCVT` 없음). 이 회차가 바꾸지 않음 |
| 4 차 이상 텐서의 배치 전치 | `widen_gemm_operand` 는 마지막 두 축의 전치만 알아봅니다. 그 밖은 예전 경로 그대로 |

## 8. README 는 무엇이라고 써야 하는가

지금 (틀림 — 원인 지목이 틀렸고, 비교 대상이 없습니다):

```
| `bfloat16` · `float16` | ... | widened to `f32` and narrowed — upstream's rule, so **slower than `f32`** |
```

제안:

```
| `bfloat16` · `float16` | ... | widened to `f32` in registers, accumulated and narrowed once — upstream's rule.
  Prefill costs 1.16x `float32` and is 2.0x faster than upstream's own `bfloat16`;
  decoding still pays for materialising the widened weight (docs/DTYPE_PERF.md §7) |
```

요점 세 가지:

1. **"upstream's rule, so slower" 의 인과가 틀렸습니다.** 규칙은 상류도 냅니다. 규칙을 그대로
   두고 2.60 배가 나왔으므로 규칙이 원인일 수 없습니다.
2. **비교 대상을 밝혀야 합니다.** "느리다" 가 *우리 f32 대비*(1.16×)인지 *상류 bf16
   대비*(0.49× — 우리가 빠름)인지에 따라 정반대로 읽힙니다.
3. **prefill 과 decoding 을 나눠야 합니다.** 하나로 뭉뚱그리면 1.16× 와 2.07× 가 섞이고,
   남은 작업(융합 gemv)이 어디에 있는지가 문장에서 사라집니다.
