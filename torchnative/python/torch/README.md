# `torch/` — 벤더링 대상 자리

여기에 상류 torch 의 파이썬 트리(BSD)를 벤더링하고 `_C` 만 교체합니다 (DESIGN.md §2).
**아직 비어 있습니다.**

`__init__.py` 를 두지 않는 것은 의도입니다. DESIGN.md §11 의 1~3 단계가 전부 **데스크톱의 상류
torch 위에서** 이뤄지므로, 지금 이 디렉터리가 `torch` 를 가리면 그 검증 경로가 막힙니다.

## 미해결 — add-hook 을 어떻게 합치나

`nn/federated.py` 는 `torchnative.nn.federated` 를 `torch` 네임스페이스에 얹는 add-hook 입니다.
상류 torch 를 소유하기 전까지 이것을 실제 `torch.nn` 아래로 합치는 방법이 정해지지 않았습니다.
§2 의 규칙은 **add-hook 은 편의이지 의존이 아니어야 한다** 는 것이므로, 이것 없이도 `torchnative`
이 온전히 동작해야 합니다.

### 배포 실험으로 좁혀진 것 (2026-08-24)

PyPI 알파를 준비하며 휠을 실제로 만들어 보고 나온 결론입니다. **산출물이 둘이고 이 디렉터리의
운명이 서로 다릅니다.**

| 산출물 | `import torch` 를 만족시키는 것 | 이 디렉터리 |
|---|---|---|
| PyPI 휠 (데스크톱) | **상류 PyTorch** — `dependencies = ["torch>=2.5"]` | **제외** |
| pypackpack 번들 (기기) | 벤더링 트리 + 우리 `_C` | 여기가 그 자리 |

데스크톱에서 우리 `_C` 는 아예 안 쓰입니다. `DESIGN.md` §11 이 검증 단계를 전부 상류 torch 위에
두는 것과 같은 이유이고, 그래서 휠이 `torch` 를 담을 이유가 없습니다.

**휠에서 `torch*` 를 제외한 것은 위생 문제이기도 합니다.** 남의 배포판 이름공간에 파일을 쓰면
pip 의 `RECORD` 를 두 배포판이 같은 경로에 대해 주장하게 되고, `pip uninstall torch` 가
우리 파일만 고아로 남겨 `torch/nn/` 이 깨진 상태가 됩니다. 상류가 언젠가 그 경로를 쓰면 정면
충돌이고요. `pyproject.toml` 의 `include = ["torchnative*"]` 옆에 이유를 적어두었습니다.

**그래서 남는 대가는 스펠링 하나입니다** — 데스크톱에서 `import torch.nn.federated` 가 안 됩니다.
`import torchnative.nn.federated` 는 어디서든 됩니다. §2 의 규칙이 이미 이것을 허용하지만,
**그 스펠링이 기기 전용이 된다는 사실은 명시해 둘 값이 있습니다.**

데스크톱에서도 그 스펠링을 원한다면 남은 수단은 `site-packages` 의 `.pth` 입니다 — 파이썬이
`import` 로 시작하는 줄을 인터프리터 시작 시 실행하므로 **torch 디렉터리에 쓰지 않고** 접붙일 수
있습니다. 대가는 `torch` 를 안 쓰는 프로세스에서도 매 시작마다 코드가 돈다는 것입니다.
**채택하지 않았습니다** — 편의 하나를 위해 모든 인터프리터 시작에 비용을 얹는 것은 §2 의
"편의이지 의존이 아니다" 를 반대 방향으로 어기는 것에 가깝습니다.
